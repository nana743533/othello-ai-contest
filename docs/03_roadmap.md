## このプロジェクトの位置づけ

**「到達力の山」として選んだプロジェクト**（2026-09-15 決定）。同日に決めた **統計検定準1級（2027年3月中旬 受験）と並行**して走らせる（本人判断: 両方フル＝到達力に週16時間）。

`profile/goals.md` の整理では、技術者の力を次の2つに分けている:

1. **技術遂行力** — 技術でプロジェクトを前に進めて成功させる力。仕事（NCS・Treee）で十分に積める
2. **技術到達力** — 難しい技術課題をどこまで深く理解・分解・解決できるか＝天井の高さ。**数学・機械学習が絡むと実力不足という危機感がある**。仕事だけでは伸びないので自主的にやる必要がある

このプロジェクトは 2 を鍛えるために立てた。9/12 の進捗ゼミ（note）で受けたFBの3基準に照らすと:

| 基準 | 評価 | 理由 |
|---|---|---|
| プロジェクト単体で価値があるか | ○ | 強いAIという動く成果物＋外部の順位という客観評価が残る |
| 現実的に達成可能か | ○ | 探索の土台（ビットボード・NegaScout・終盤完全読み）は 2026-07 に実装済み。ゼロからではない |
| 本人が優位性を持っているか | ◎ | **競技オセロ日本5位**。評価関数の特徴量設計と「AIの手が良いか」の判断で、他の人が持っていない直感がある |

**最大のリスク: この山は「C++高速化ゲーム」に逃げられてしまう。** 探索の最適化だけをやると、結局は遂行力の訓練にしかならず、この山を選んだ意味が消える。だから完了条件に「**評価関数を自分で学習させ、その効果を数字で示す**」を必ず入れる（Phase 2）。

## ゴール

- **学習面（本命）**: 評価関数を機械学習で作り、Multi-ProbCut を統計で設計する。＝線形回帰・勾配降下・正則化・区間推定・検定を「使って結果が出る場所」で使う
- **成果面**: CodinGame Othello アリーナで順位を上げる

### 完了条件（案）

1. 自作の学習済み評価関数が、手書き評価関数に自己対戦で**勝ち越す**（数字で示す）
2. Multi-ProbCut を入れて、同じ持ち時間で読める深さが増えたことを示す
3. CodinGame アリーナで **上位10%（638人中およそ60位以内）**

# フェーズ

## Phase 0 — まず提出して現在地を測る（最優先・1〜2時間）

Kaggle と同じで、**まず1回通す**。順位という基準点が無いと以降の改善が測れない。

- [ ] CodinGame にログインし、Othello アリーナに JOIN する
- [ ] `cpp/submit.cpp` を貼って提出 → **初期順位を記録する**（638人中何位か）
- [ ] Boss（darkhorse64作）に勝てるか確認する
- [ ] IDE で**実際の思考時間制限を確認**し、`01_io_spec.md` の記述（初手2000ms/以降150ms）が正しいか検証する
- [ ] TLE・不正手で落ちていないか、対戦リプレイで確認する

## Phase 1 — 探索の土台を仕上げ、測定環境を作る（2〜3週）

ここは engineering（遂行力側）。**深入りしすぎないこと。** Phase 2 に進むための土台。

- [ ] `cpp/src/` の実装（bitboard・NegaScout・TT・終盤完全読み）を `submit.cpp` に統合し、1ファイルで提出できる形にする
- [ ] **反復深化＋時間管理**を入れる（150ms を安全マージン付きで使い切る。タイムアウトは即敗北なので最重要）
- [ ] move ordering を詰める（置換表の最善手 → 角 → 評価値順）
- [ ] **★ ローカル自己対戦フレームワークを作る**（N局回して勝率・信頼区間を出す）
  - これが無いと「強くなったのか」が分からず、以降のすべての改善が博打になる。**このフェーズの本命はこれ**
  - 順位は対戦ノイズが大きく反映も遅いので、**主指標はローカル自己対戦勝率**にする
- [ ] 改善のたびに「vs 1つ前のバージョン 勝率」を記録するログを残す

**到達目標**: 提出して中位以上。以降どの施策が効いたかを数字で言える状態。

## Phase 2 — 評価関数を「学習」させる（本命・6〜10週）

**ここがこのプロジェクトの存在理由。** 強いオセロAI（Logistello、Egaroucid）は手書きの評価関数ではなく、**パターン特徴＋大量データからの学習**で評価関数を作っている。

- [ ] **パターン特徴（n-tuple）を設計する** ← 競技オセロの知見が直接効くところ
  - 定番: 辺＋X打ち、角の3x3、対角線、横列・縦列
  - 「なぜこのパターンか」を自分の対局感覚で説明できるようにする。ここが優位性
- [ ] **学習データを用意する**
  - 自己対戦で局面を大量生成する、または公開棋譜DB（WTHOR＝フランスオセロ連盟の大会棋譜）を使う
  - ラベル: 最終石差、または深い探索の評価値
- [ ] **モデルを学習する**
  - ステージ別（空きマス数で区切る）に線形モデルを持つ
  - 最小二乗法／ロジスティック回帰、確率的勾配降下法（SGD）
- [ ] **検証する**
  - train/validation 分割、過学習の確認、正則化
  - 最終判定は「学習済み評価関数 vs 手書き評価関数」の自己対戦勝率
- [ ] 提出して順位の変化を記録する

**ここで身につく数学・ML**: 特徴量設計 / 最小二乗法 / 勾配降下法 / 正則化 / 過学習と汎化 / train-val 分割 / 評価指標の設計

**教材**:
- `life-management/knowledge/study/20260815_game-ai-deep-rl.md`（**作成済み・未読**。7章にオセロAlphaZero実装コード）
- Michael Buro "Experiments with Multi-ProbCut and a New High-Quality Evaluation Function for Othello"（1997）— パターン評価関数の原典
- Egaroucid のソース（`reserch/Egaroucid/` に fork 済み）

## Phase 3 — Multi-ProbCut（統計の実地・3〜4週）

**統計検定準1級で迷っていた内容が、そのまま道具として出てくる場所。**

浅い探索のスコアから深い探索のスコアを予測し、「深く読んでも結論は変わらない」と統計的に言える枝を切る手法。

- [ ] 浅い探索スコアと深い探索スコアの組を大量に集める
- [ ] **線形回帰**で関係を推定し、**残差の標準偏差 σ** を見積もる
- [ ] 閾値 t を決めて前向き枝刈りを実装する（t は「どれだけ切り捨てを許すか」＝検定の有意水準の話）
- [ ] 同じ持ち時間で読める深さがどれだけ増えたか、勝率がどう動いたかを測る
- [ ] Buro "ProbCut: An Effective Selective Extension of the α-β Algorithm"（1995）を読む

**ここで身につく統計**: 回帰 / 残差と分散の推定 / 区間推定 / 検定の考え方 — **準1級の「使う章」と同じ範囲を、答え合わせができる場所で使う**

## Phase 4 — 詰めと順位上げ（継続）

- [ ] 定石（opening book）を作る
- [ ] 終盤完全読みを深くする（parity、Enhanced Transposition Cutoff、Null Window Search）
- [ ] 提出 → 順位変動を記録 → 効いた施策だけ残す、を回す
